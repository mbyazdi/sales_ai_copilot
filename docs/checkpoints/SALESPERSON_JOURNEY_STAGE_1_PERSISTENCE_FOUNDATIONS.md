## Exact models and ownership

### sales_requests.SalesRequest

- A protected OneToOne Visit relation is the database-enforced one-request-per-
  visit MVP rule. The same header moves from DRAFT to SUBMITTED; no extra state.
- Customer/salesperson are derived properties of the authoritative Visit, not
  duplicated foreign keys. Queries must use visit__customer / visit__salesperson.
  This prevents contradictory request/visit owner/customer combinations at creation.
- Nonnegative integer revision starts at 0. It is not automatically incremented.
- Nullable unique number and submission UUID, nullable validated SHA256 intent
  fingerprint, nullable submitted_at, draft note and created/updated timestamps.
- Nullable Decimal base/discount/final totals and currency; customer, salesperson
  and pricing JSON snapshots; prepared_message_snapshot text.
- Submitted validation requires supplied metadata, totals/currency, actual
  persisted Visit identity, captured customer code/name and salesperson code/name,
  and at least one complete selected line snapshot. No number, amount, message,
  grade discount, eligibility or commercial fact is generated by these checks.

### sales_requests.SalesRequestLine

- Protected request and Product references; required positive integer quantity.
  Fractional/boolean quantities are rejected rather than truncated.
- is_selected plus removed_at permits retained removed lines. The database
  requires consistent selected/removal metadata and one selected product line per
  request. Re-add history can use another line after the earlier line is retired.
- ORDINARY has no recommendation; RECOMMENDATION requires a protected existing
  recommendation FK. The database checks the source/FK pairing.
- Model validation checks recommendation customer/product against persisted
  request/Visit/product data, including when supplied related instances contain
  unsaved changes. Existing line identity and captured lineage cannot be reassigned.
- product_snapshot, lineage_snapshot, eligibility_snapshot and pricing_snapshot
  are JSON objects. Recommended lineage preserves the linked recommendation ID
  and caller-supplied evidence; no evidence or priority is fabricated.
- Nullable base_unit_price, discount_percentage, discount_amount, final_unit_price,
  line_total, currency, pricing_source and pricing_version. Unknown draft quotes
  are NULL, not fake zero prices. Supplied monetary values are nonnegative and
  discount percentage is bounded 0–100. The only known currency is TOMAN.
- A submitted line requires all quote fields plus product ID/code/name/unit.
  Model code neither computes amounts nor verifies discount/total arithmetic;
  the future trusted pricing/submission service must supply and validate that.

### sales_requests.SalesRequestAcknowledgement

- A protected OneToOne submitted-request relation, protected Salesperson actor,
  acknowledged_at and JSON metadata.
- Append-only; actor must match the persisted Visit owner. Cached/unsaved request
  status does not permit acknowledging a draft.
- Acknowledgement does not update the submitted header or complete the Visit.
  The explicit protected completion orchestration remains a later stage.

### products.ProductDemoPrice

- Protected OneToOne Product reference: one controlled current demo price row.
- Required Decimal base_price, TOMAN currency, nonblank source/source_version,
  created_at and updated_at. No amount/currency/source default supplies fake data.
- Database guards nonnegative price, supported currency and nonempty source/version;
  model validation also rejects whitespace-only source identifiers.
- Mutable current-source data is separate from submitted request price snapshots.
  No provider, grade rule, calculation, fallback, historical-price lookup or seed.
- The optional product-image schema proposal is deferred to keep this foundation
  minimal; no image/master-data field, media integration or image seed was added.

### recommendations.RecommendationFeedbackEvent

- Append-only ADDED_TO_REQUEST, REMOVED_FROM_REQUEST or REJECTED records, separate
  from legacy SalesOutcome/PURCHASED and realized Sale/SaleItem.
- Protected Visit/recommendation references; optional protected request/line
  references; created_at, lineage JSON, structured reason code and optional note.
- The seven approved rejection reasons are represented by stable choices. Reasons
  are required for REJECTED and absent for add/remove. Add/remove require a line
  and request; a line cannot be attached without its request.
- Model validation checks persisted customer, request visit, line/product and exact
  recommendation identity. Product is derived from the recommendation; no drifting
  duplicate product FK is stored. A recommendation is mandatory, excluding fake
  feedback for ordinary lines.
- Recommendation deactivation remains supported; old linked evidence/IDs remain.
  History can record add then remove without deleting/rewriting the add or
  implicitly creating REJECTED, FOLLOW_UP or legacy PURCHASED.
- No events are automatically emitted. Later services must prove legitimate
  saved-session prioritization, handle revision/idempotency and append facts within
  the same transaction as the corresponding explicit mutation.

## Lifecycle and immutability protection

Request status and submission-field consistency are database-checked. Submitted
headers and their lines reject normal model saves/deletes, including stale objects
and attempts to revert status or move a line to another header. New lines cannot
be added to a submitted request. Header Visit identity cannot be changed even in
DRAFT. Events and acknowledgements reject existing-record updates/deletes.

Guarded model saves run full_clean in transaction.atomic. Parent checks use fresh
persisted state; line writes lock the parent where the database supports it.
Retained completed/cancelled-visit drafts are read-only. Closing a Visit itself
does not mutate or submit its draft, and no-sale completion remains unchanged.

Public QuerySet update/bulk_update/bulk_create cannot bypass protected-model
validation. QuerySet deletion checks protected rows. Request revision-only updates
remain available for later compare-and-set operations; SQL predicates exclude
submitted/closed-visit rows. The future service must still supply expected revision
and own the transaction: Stage 1 does not implement a basket concurrency workflow.

Protected FK relationships prevent accidental cascading deletion of request,
lineage and history through Visit/Product/Recommendation removal. Recommendation
regeneration by deactivation remains valid. These are deliberate historical-data
protections and may require later controlled handling in demo maintenance.

No database triggers were added. Raw SQL, save_base/private ORM methods and
uncontrolled base-manager writes are outside the guarded persistence path and can
bypass model rules. Later write APIs/services must use the validated boundary;
SQLite revisions, authorization, pricing/stock revalidation and full cross-process
submission idempotency are not claimed to be implemented by these models alone.

Visit relationships remain owned by the existing visits domain. Stage 1 does not
change any Visit reassignment policy; submitted identity snapshots preserve the
historical identities even if master data later changes. Any future reassignment
feature needs explicit ownership/history policy and current-access guards.

## Corrective patch — partial submission save

The read-only audit found a public ORM hazard: GuardedModel.save validated the
complete in-memory SalesRequest but passed update_fields unchanged to Django.
An existing DRAFT could therefore become SUBMITTED through
`save(update_fields=["status", "submitted_at"])` while required customer,
salesperson/pricing snapshots and prepared message stayed empty in the database.
The incomplete row then became immutable. The initial test suite did not cover it.

The correction is a six-line SalesRequest.save override only. If in-memory status
is SUBMITTED and update_fields is not None, reject with ValidationError before
the shared save/validation/persistence path. Stage 1 deliberately rejects even a
complete non-None field list and an empty field list. No fields are silently added.
Omitting update_fields or explicitly supplying None retains the full guarded save.
Existing submitted rows still reject full saves through the original persisted-
state guard; an unsaved status reversal does not permit a partial update.

No shared guard, line/event/acknowledgement semantics, schema, migration, pricing,
legacy outcome or UI behavior was changed. Ordinary draft partial saves retain
their original field-projection behavior.

Eight explicit regression tests in PartialSubmissionSaveRegressionTests cover:

- valid in-memory submission rejected for list/tuple/set, incomplete/complete and
  empty update_fields; zero INSERT/UPDATE/DELETE/REPLACE queries, exact unchanged
  persisted row, DRAFT status and untouched snapshots;
- a subsequent full save persists complete submitted snapshots and remains immutable;
- update_fields=None is still a full valid save;
- non-transition draft header and line partial updates remain partial;
- new append-only feedback/acknowledgement partial saves cannot insert records;
- all original 24 normal ORM protection combinations remain blocked;
- existing submitted/append-only partial saves and unsaved reversal attempts fail.

Adjacent-path review found no independent equivalent blocker. A line has no
mutable-to-frozen status transition: partial quote updates remain in a draft, and
full header submission validates complete line snapshots loaded from the database.
Feedback and acknowledgement are append-only: existing-record saves are rejected;
new records cannot be inserted with update_fields through Django's forced-update
path. No adjacent model was redesigned or modified.
